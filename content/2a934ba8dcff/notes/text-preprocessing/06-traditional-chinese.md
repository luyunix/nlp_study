## 真正看懂本节：能读取繁体，不等于已经处理好繁体

Python 3 能正确保存 `軟體更新失敗`，说明字符编码没有损坏；分词器能否把 `軟體 / 更新 / 失敗` 切得合理，则取决于词典覆盖。**字符可表示性**和**语言处理质量**是两个不同问题。

### 简繁转换会改变哪些数据

客服语料可能同时出现：

```text
简体：软件更新失败
繁体：軟體更新失敗
```

若任务是跨地区搜索，把两者额外映射到同一规范化字段有助于互相召回；若任务要生成原文、保留人名商标或分析地区用词，只保存转换结果会丢信息。稳妥的数据结构是：

```text
raw_text        = 原始输入
normalized_text = 为当前任务生成的规范化副本
```

模型可以使用 `normalized_text`，展示与审计仍回到 `raw_text`。不要原地覆盖原文。

### 为什么机械转换可能产生歧义

字形转换不是纯粹“一字换一字”；不同地区词汇可能完全不同，同一个简体字也可能对应多个传统字形或语义。转换后看起来字符统一，不代表措辞、专名和含义都统一。必须在真实业务样本上检查：

- 常见地区词是否仍为整体；
- 人名、地名、品牌是否被改坏；
- 转换前后标签含义是否保持；
- 训练和预测是否使用同一套转换规则。

### 一个最小对照实验

准备包含通用词、地区词和专名的 20–50 条小样本，分别对原文与规范化文本分词。记录错误类型，而不只比较 token 数。若转换让搜索召回提高，却破坏专名，就应在索引中同时保留原词与规范词，而不是二选一。



## 零基础精讲：把这一节慢下来

### 先看一个具体场景

客服数据可能同时出现“软件”和“軟體”。程序能保存这些 Unicode 字符，但词典是否认识地区用语，决定了切分是否合理。

### 数据究竟怎样一步步变化

1. 原样保存繁体文本
2. 确认读取和写出都使用 UTF-8
3. 用支持繁体的分词词典匹配
4. 按业务决定是否另存规范化版本

把上面四步和流程图对照起来：

> 繁体文本 → Unicode 字符串 → jieba 词典匹配 → 繁体词元

这里的箭头表示“左边的数据经过一次处理，变成右边的数据”，不是四个需要孤立背诵的名词。

### 第一次读代码，只盯住这一件事

先直接分词，不要先转换字形。观察接口是否与简体文本完全相同，再检查结果中的地区词。

## 最小可运行代码

在项目根目录运行下面代码。课程原理的标准库版本集中在 [text_preprocessing_from_scratch](../../text_preprocessing_from_scratch/README.md)；需要 jieba、PyTorch、FastText 等的示例，请先按代码注释安装依赖。
